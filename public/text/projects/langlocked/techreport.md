Lang Locked has been a super interesting project to implement. It has required a whole lot of learning in many different areas, so I'll split them into a few subheadings below. These are in order of learning. The project is ongoing, so this may be outdated.
### Fabric MC GUI Drawing
The first thing I had to do in this project was learning FabricMC and how it worked. I more or less jumped straight into what I was trying to do, ignoring any item, block, or entity modding to jump straight to GUI. Nothing was *super* interesting here, other than my discovery that I can mess with the rendering of the game in it's entirety. I wanted to make the item display twice as large, so I simply pushed a scale by 2 matrix onto the JOML stack. Turns out that stack affects all UI, so I messed up the global GUI for a minute there. Ultimately I got through it and successfully drew a box, the item, its name in Korean, and a timer bar at the bottom of the popup. This was all triggered with /forcechal for the time being.
### Handling Hangul Pronounciation
The next thing I really had to do was add the Hangul to the screen. This wasn't really a difficult job at all, as Minecraft has native support for a lot of languages, Korean included. All I had to do was load this language file (stored in JSON) and make a Map from English to Korean. 

The thing is, I thought it would be *really* nice for learning to not just display the Hangul, but also the pronounciation in the Latin alphabet too. This ended up being a deep rabbit hole. I'd been learning Korean for a sizable amount of time already, so I figured it wouldn't be too bad, but the number of edge cases was annoyingly large. I ended up writing a script that takes in a compound character, decomposes it (using an external library, although I did later find out there are formulas to get the UTF-8 for each of the individual characters), and gives back the sound that the character makes, taking into consideration whether it leads or ends a syllable. I'm not going to pretend this is perfect. There are flaws, such as bachim handling (characters like 넓). I know that these are pronounced slightly differently, but the script treats them as the same as other, single characters. Another known issue of this approach is how the actual pronounciation of some words just doesn't match the characters exactly. (I'm lucky I wasn't doing this in reverse for English!) For example, 감사합니다 would show up as pronounced "gam-sa-hab-ni-da," whereas actual Korean speakers tend to pronounce it "gam-sa-ham-ni-da." (Of course, the word for thank you wouldn't show up, but I'm sure there are some words in there that aren't quite right)
### OS-level Text to Speech (TTS)
After adding in the pronounciation, I thought it could be helpful to also have the game *say* the word to you as well. This was a pretty long and winding road of research that landed in a pretty simple conclusion. I spent several hours searching for and trying different TTS models, but all didn't take Hangul and the pronounciation method seemed *iffy.* Eventually, a friend of mine suggested using OS-level built in TTS. Turns out, MacOS has a really robust TTS engine for a ton of languages built in. Windows isn't quite as nice, as it requires explicitly adding the TTS voice to your settings, but it works fairly well. As for Linux, I haven't even tried. All my Linux machines are CLI only, so I haven't really tested this at all there. With these TTS engines, all I had to do was call them, which, admittedly, I'm not very proud of my method. I run a terminal command on each OS to say whatever it is I want. It works, but is certainly a little iffy.
### Vosk Speech to Text (STT)
Next up, after adding all of the support tools, I needed to do the hard part: making the system actually interactive. Up to this point, I'd successfully made a pop-up that asks you to say something in Korean, but nothing at all actually checked if you a.) said anything and b.) said what you were told to. This is where Vosk comes in. After a bit of research into speech to text, I finally found something that might fit my usecase: Vosk. I chose Vosk over things like Cheetah for two key reasons: 1.) Vosk supports Korean! This is really the big one. Non-negotiable. 2.) Vosk is an offline model! This second one I was *willing* to compromise on if I absolutely had to, but Vosk fits my use case fairly well AND isn't too large (~250MB) for the ko-0.22 model (the only Korean model as far as I could tell). This is the part that really turned this project into an explicitly *Korean* learning tool rather than general language learning, although modifying my code for other languages wouldn't be *too* hard.

Okay that's enough preamble. Let's talk about the dragon that is implementing Vosk ko-0.22 with Simple Voice Chat. Running Vosk itself was really easy. It was just a handful of calls to load the model from file and actually getting output was just as easy. I implemented a Python script that reads a .wav and outputs Hangul in no more than 20 minutes. Doing so with Simple Voice Chat as a live mic input was much harder though. I had to plug in to the Simple Voice Chat system to run the Vosk model any time the client was recieving voice input from the mic. If you know much about how text is handled in computers, this is interpreting binary incorrectly. I assumed that meant there was an encoding issue, a theory confirmed by Googling that exact string and getting an AI overview response in Korean. ### Levenshtein Distance and Judjing Correctness
I quickly realized that it is not reasonable to expect Vosk model to produce 100% accurate output and I knew that given this, people would find this very frustrating. It was *rare* for the engine to recognize my Korean (which, I'll admit, isn't perfect, but that's kind of the ideal target user!), so I couldn't just rely on comparing the expected word and the output of Vosk. That's when I started looking into ways to compare string similarity, which very quickly got me to Levenshtein distance, an algorithm that I was familiar with, but had completely forgotten about. I looked at the Wikipedia page and was immediately thrilled to see a D(i,j) representation, meaning this was going to be a dynamic programming problem (my favourite kind of programming!) I wrote a quick Python implementation just to ensure quick debugging (at this point, the mod took around a minute to compile). While doing so, I realized that I probably want to be as generous to the user as possible. Therefore, I decided to use the weighted Levenshtein distance for the Hangul, the individual Jamo string, and the pronounciation representation and give the user the lowest of the three.
